# V3 — From Learning App to Operator Training Platform

The thesis: a robot vendor sells hardware to a factory. The factory's operators
need to learn how to run it safely, prove they learned it, and stay certified.
Today's product trains an individual who enrolls themselves; V3 makes the
*organization* the customer and turns the tutor into training infrastructure.

The loop the product must close:

```
Author  →  Assign  →  Train  →  Assess  →  Certify  →  Report
(vendor)   (supervisor) (operator,  (oral exam   (expiring    (audit
            + deadline)  exists ✅)   by tutor)    credential)   trail)
```

We have "Train" built end-to-end (voice + chat + whiteboard + materials).
Everything else is missing — but less is missing than it looks.

---

## 1. What the codebase already gives us

### 1.1 Multi-tenancy is half-built

`packages/db/prisma/schema.prisma` already has:

- **`Workspace`** with `clerkOrganizationId String? @unique` and
  `kind String` — the org mirror table *exists*. It has only ever been fed
  `kind: "personal"` workspaces by `apps/web/src/lib/learner.ts`, which
  provisions one per learner on first sign-in.
- **`workspaceId` columns on nearly everything**: `Session`, `ContextSource`,
  `MasteryObservation`, `Summary`, `LessonCheckpointRecord` all carry an
  optional `workspaceId` with indexes. Tenancy scoping was designed in from
  the start; it's just unused.

So "add organizations" is not a schema rewrite. It's: feed the existing
`Workspace` table org rows from Clerk, resolve the active workspace in
`getLearnerContext()`, and start writing real `workspaceId`s.

### 1.2 The audit trail is already the killer feature

`SessionEvent` is an append-only, sequenced log of everything that happened in
a training session — every utterance (`TranscriptProjection`), every
whiteboard action, every checkpoint. For compliance training this *is* the
product: verifiable evidence that operator X covered procedure Y on date Z,
down to the transcript. No LMS competitor has this naturally; we get it for
free from the harness architecture.

### 1.3 Mastery primitives exist

`MasteryObservation` (conceptKey, signal, level, confidence, note) is written
by the live agent's tools today (`apps/agent/src/tools.ts`). It's an
unstructured stream; certification needs it rolled up against a rubric — but
the raw signal collection already works.

### 1.4 The teaching-intent layer exists

`Lesson.objectives[]` and `Lesson.conceptKeys[]` already drive the tutor's
system prompt (`packages/tutor/src/prompt.ts`). A course builder is mostly
CRUD over `Course` / `CourseModule` / `Lesson` rows that are currently
seeded by script — authoring these fields *is* authoring the tutor.

### 1.5 What's genuinely missing

| Gap | Detail |
|---|---|
| Org provisioning | Nothing creates `kind: "org"` workspaces or syncs Clerk org membership |
| Role model | No concept of supervisor vs operator anywhere in app code |
| Course ownership | `Course` has no `workspaceId` — all courses are a single global catalog |
| Course-scoped materials | `ContextSource` is learner-scoped; vendor can't upload a manual once for everyone (`apps/web/src/lib/tutor-service.ts` loads materials by `learnerId`) |
| Assignment | `Enrollment` is self-service; no assigner, no due date, no "required" |
| Assessment | No pass/fail anywhere; sessions never conclude with a verdict |
| Certification | No credential, no expiry, no recertification trigger |
| Reporting | No supervisor-facing view of anyone else's data; no transcript viewer |
| Authoring UI | Courses/modules/lessons only enter the DB via seed scripts |

## 2. What Clerk Organizations actually covers

Verified against Clerk docs (2026):

- **Orgs + membership + switcher.** Users belong to multiple orgs; the session
  carries the *active organization* (`auth()` returns `orgId`, `orgRole`).
  `<OrganizationSwitcher />` is a drop-in. This maps to our footer/sidebar
  cleanly.
- **Roles.** Default `org:admin` / `org:member`, plus custom roles (e.g.
  `org:supervisor`, `org:operator`) defined once at the application level,
  manageable via dashboard or Backend API (`POST /v1/organization_roles`).
  Authorization checks via `has({ role: "org:supervisor" })` server-side.
- **Custom permissions** tied to features (e.g. `org:training:assign`,
  `org:reports:read`) assignable to roles — useful later so we gate on
  permissions, not roles.
- **Onboarding paths.** Invitations (bottom-up), **Verified Domains**
  (auto-invite everyone `@factory.com` — ideal for a plant rollout), and
  Enterprise SSO (SAML/OIDC) when a customer's IT department demands it.
  We write zero code for any of these.
- **Webhooks.** `organization.created`, `organizationMembership.created`,
  etc., signature-verified via `verifyWebhook`. This is how the `Workspace`
  mirror stays in sync (same pattern we'd use for `user.created` → `Learner`).

What Clerk does **not** do: anything domain-specific. Which courses an org
owns, who's assigned what, assessment results, certificates — all ours.

Division of labor: **Clerk answers "who are you and what's your role here";
our DB answers "what training does this org run and where does everyone
stand."**

## 3. Data model changes

### 3.1 New tables

```prisma
// Mirrors Clerk org membership so queries never need a Clerk API call.
model WorkspaceMember {
  id          String   @id
  workspaceId String
  learnerId   String
  role        String   // "admin" | "supervisor" | "operator" (mirrors org role)
  createdAt   DateTime
  updatedAt   DateTime @updatedAt

  @@unique([workspaceId, learnerId])
}

// Supervisor assigns a course to an operator. Supersedes self-enrollment
// in org contexts (Enrollment stays for personal/consumer use).
model Assignment {
  id           String    @id
  workspaceId  String
  courseId     String
  learnerId    String
  assignedById String    // WorkspaceMember/Learner id
  required     Boolean   @default(true)
  dueAt        DateTime?
  status       String    // "assigned" | "in_progress" | "completed" | "overdue" | "waived"
  completedAt  DateTime?
  createdAt    DateTime
  updatedAt    DateTime  @updatedAt

  @@unique([workspaceId, courseId, learnerId])
  @@index([workspaceId, status])
  @@index([learnerId, status])
}

// Authored pass criteria for a course (or lesson). The oral-exam rubric.
model Competency {
  id          String  @id
  courseId    String
  lessonId    String?
  conceptKey  String  // joins against MasteryObservation.conceptKey
  title       String
  rubric      String  // what "passing" sounds like; fed to the assessor prompt
  passLevel   String  // minimum MasteryObservation.level to pass
  orderIndex  Int
}

// One assessment run — a session in "exam mode" with a verdict.
model AssessmentAttempt {
  id          String    @id
  workspaceId String?
  learnerId   String
  courseId    String
  sessionId   String    // full transcript evidence lives in SessionEvent
  status      String    // "in_progress" | "passed" | "failed" | "abandoned"
  score       Json?     // per-competency results
  decidedAt   DateTime?
  createdAt   DateTime
}

model Certificate {
  id          String    @id
  workspaceId String?
  learnerId   String
  courseId    String
  attemptId   String
  issuedAt    DateTime
  expiresAt   DateTime? // compliance certs lapse; null = perpetual
  revokedAt   DateTime?
  serial      String    @unique // public verification token

  @@index([workspaceId, expiresAt])
  @@index([learnerId])
}
```

### 3.2 Modified tables

- **`Course`**: add `workspaceId String?` (null = global catalog, set = owned
  by vendor org) and `visibility` (`"private"` to the org, `"licensed"` to
  customer orgs, `"public"`). Licensing between vendor org ↔ factory org can
  start as a simple `CourseLicense` join table when needed; day one, a vendor
  can run training inside its customers' workspaces directly.
- **`ContextSource`**: today `learnerId` is required. Make course-level
  materials possible: add `courseId String?`, relax learner scoping so
  `sourceType: "course_material"` rows attach to the course, uploaded by an
  admin. `loadSessionMaterials()` in `apps/web/src/lib/tutor-service.ts`
  then loads `(course materials) ∪ (learner uploads)` instead of filtering
  the learner's uploads by a `courseId` key in the JSON `content` blob
  (the current hack — see `apps/web/src/app/(app)/courses/[courseId]/materials/page.tsx`).
- **`Session`**: add `kind String @default("learning")` —
  `"learning" | "assessment"`. Assessment sessions get a different system
  prompt (assessor, not tutor) and refuse to leak answers.

### 3.3 What deliberately does not change

`SessionEvent`, projections, the tutor/agent harness, uploads pipeline —
untouched. Assessment is *a session with a different prompt and a verdict
writer*; reporting is *queries over data we already write*.

## 4. Auth & provisioning changes

1. **Enable Organizations** in the Clerk dashboard; create custom roles
   `org:supervisor` and `org:operator` (keep `org:admin` as-is).
2. **Webhook route** (`/api/webhooks/clerk`): `organization.created` →
   upsert `Workspace { kind: "org", clerkOrganizationId }`;
   `organizationMembership.*` → upsert/delete `WorkspaceMember` (and
   provision a `Learner` if the user has never signed in). Verify signatures
   with `verifyWebhook`.
3. **`getLearnerContext()`** (`apps/web/src/lib/learner.ts`): read
   `orgId` from `auth()`. If an org is active, resolve its workspace +
   the member's role; else fall back to the personal workspace (current
   behavior, fully preserved — the consumer mode stays free).

   ```ts
   type LearnerContext = {
     learnerId: string;
     workspaceId: string;
     role: "admin" | "supervisor" | "operator" | "personal";
     displayName?: string;
   };
   ```
4. **Sidebar**: `<OrganizationSwitcher />` (themed) above the search field.
   Role-gate the admin nav group.

## 6. Phases

Each phase ships independently and nothing later blocks on perfection earlier.

### Phase 1 — Organizations (foundation)
Clerk orgs enabled, custom roles, webhook → `Workspace`/`WorkspaceMember`
mirror, `getLearnerContext()` org-aware, `OrganizationSwitcher` in sidebar,
role-gated empty `/admin` shell.
**Proof:** two test users in one org see shared workspace context; personal
mode unaffected.

### Phase 2 — Course-scoped materials + course builder
`ContextSource.courseId`, admin upload of course materials,
`loadSessionMaterials()` merges course + learner materials, builder CRUD for
courses/modules/lessons (replaces seed-script-only authoring).
**Proof:** admin uploads a "robot manual" PDF; every enrolled operator's tutor
cites it.

### Phase 3 — Assignments
`Assignment` model, `/admin/assignments`, "My training" home for org
contexts, completion inference (all lessons touched → suggest complete;
explicit completion comes with Phase 4 assessments).
**Proof:** supervisor assigns course with due date; operator sees it, trains,
status board updates.

### Phase 4 — Assessment + certification
`Competency` authoring in builder, exam-mode sessions (assessor prompt +
verdict tool writing `AssessmentAttempt.score` from rubric-checked
`MasteryObservation`s), `Certificate` issuance with expiry,
`/certificates` + `/verify/[serial]`.
**Proof:** operator passes an oral exam conducted by the voice agent; cert
issued; failing genuinely fails.

### Phase 5 — Reporting + audit
`/admin/reports`, transcript viewer, CSV export, cert-expiry surfacing
(in-app first, email later).
**Proof:** safety officer can answer "who is trained on the new arm, and show
me the evidence" in two clicks.

### Deliberately deferred
Simulation/AR, SCORM/LTI, multi-language, offline/kiosk mode, billing &
seat licensing, cross-org course marketplace, automated retraining triggers
on firmware updates. All real, all premature.

## 7. Open questions

1. **Vendor ↔ factory relationship.** Does the robot vendor operate *inside*
   each factory's org (simplest: vendor staff are members), or do we need
   first-class cross-org licensing (`CourseLicense`) from day one? Start
   with the former.
2. **Assessment integrity.** Is voice oral-exam sufficient for compliance, or
   do some certs require proctored/structured quizzes? (Affects whether
   Phase 4 needs a question-bank format too.)
3. **Operator identity.** Floor workers may not have company email —
   does Clerk's username/phone auth cover the workforce, or do we need
   badge-code sign-in eventually?
4. **Cert authority.** Are certificates issued by the vendor, the factory, or
   the platform? Affects branding on `/verify/[serial]` and who can revoke.
5. **Harness extraction timing.** Exam-mode sessions are a second consumer of
   the turn pipeline — Phase 4 is the natural moment to do the TODO.md
   harness extraction so tutor/assessor are two configurations of one
   runtime, not a third copy.
